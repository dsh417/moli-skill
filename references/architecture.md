# Architecture — 架构与协作

Moli 做过 SLG 服务器、PC 网游、手游、独游。核心信条：**规矩是给"长期+多人"项目的成本**，不是给写得爽的。小项目可以随便；一上规模，就得守。

---

## 多种实体都需统一操作时，用统一容器作基底，哪怕 size=1

**为什么**：先写 Unit 类再后置抽象 IOperation 接口，会为每种 Unit 写独立的操作逻辑，最后长成屎山；一开始就以 Group 为基底，塔是 size=1 的 Group，兵是 size=N 的 Group，所有操作无特例。

**示例**（RTS）：
```csharp
// bad: 兵是 Group，塔是 Unit，UI 要分别处理两种选中
// good: 兵和塔都是 Group，UI 只处理 Group
//       塔的 Group 只含一个单位
interface ISelectable { Group AsGroup(); }
class Tower : ISelectable { Group AsGroup() => new Group(new[] { this.unit }); }
class Squad : ISelectable { Group AsGroup() => this.group; }
```

Moli 原话："屎山是充满了各种特例，和为特定业务而插桩的代码；统一的 group 设计使得所有操作没有了特例，统一操作上的基本单位。"

## 多人协作频繁合并冲突，先检查分工或架构耦合，再想流程

**为什么**：冲突多是分工切面有严重耦合（两人改同一模块/同一文件结构）或架构设计不清的症状；工具/流程层面的补丁（频繁 rebase/小步提交）只是治标。

**示例**：
```
bad: 买 GitHub Enterprise / 配 merge driver / 规定小步提交
good: 先画模块边界图，把两人的任务切到几乎不碰彼此文件的两个子系统
```

---

## 重构时机由"开发效率受损"决定，不看代码行数或完成度

**为什么**："写到 2000 行该重构"是伪标准；真正的信号是**新业务不断叠加导致原架构不适用，继续写下去效率明显下降**。

**示例**：
```
bad: 定个"单类超过 1500 行就重构"的规则
good: 观察感受："这几天改这个模块每次都要改 5 个地方、漏一个就崩" → 重构
```

Moli 原话："通常重构不是到了多少行，然后要重构，而是因为不断叠加的非预期的业务，导致针对之前场景设计的架构已经不适应现在新的需求，如果不重构会导致开发效率降低，所以才重构。"

---

## 代码严谨度随项目规模/人数/维护周期线性提高

**为什么**：多人长期维护时，脆弱架构会随业务叠加拖垮开发效率——加个功能就连锁崩；规范/可维护性/设计是为"长期+多人"服务的成本，不是为"写得爽"。

**示例**：
```
自己练手 demo：奔放写无所谓
3 人以内短期：基本命名+简单模块划分就行
超过 3 人参与 or 预计维护一年以上：边界清晰、命名规范、公共接口稳定
大型长期（>10 人, >3 年）：规范到可以换一个人开发立刻能上手
```

Moli 原话："越大，参与人越多的项目，对规范、对可维护性、对设计的要求就越高——这些要求都是为了在长期开发中，不会负担越来越重，到最后，随便加一个功能，整个系统就出现一堆问题；也不会换一个人开发，无从下手。"

## 事件/信号的回调优先用独立函数，不要现场写 lambda

**为什么**：lambda 捕获栈变量会生成一个隐式闭包类，容易无意间把很大的上下文捕进去；独立函数签名清晰、捕获显式、生命周期可控、调试栈好看。

**示例**：
```csharp
// bad
button.OnClick += () => { DoThing(_player, _state, _env); };

// good
button.OnClick += OnButtonClick;
void OnButtonClick() { DoThing(_player, _state, _env); }
```

---

## 跨平台库抽象停在"SDK 业务契约"层，不要下探到"渲染/IO 原语"

**为什么**：不同平台的最佳实现天差地别（Unity 合批 / WebGL / DX / Flash stage3d）；强行抽象统一的 RHI（渲染硬件接口）要么牺牲每个平台的 native 优势，要么接口庞大到必须再包一层 platform-native。Spine / FairyGUI 的做法——只定义顶点输出/编辑器白皮书这类业务契约，每平台 SDK 用 native 方式独立实现——才是对的。

**示例**：
```
bad: 定义 IRenderer { DrawMesh, SetTexture, ... } 每平台实现一套
good: 定义"编辑器输出的数据结构 + 每平台 SDK 公开 API 契约"
      内部各自走 native（Unity 用 Graphics.DrawMesh，Flash 用 stage3d shader...）
```

Moli 的核心论点：
- "你同一个语言可以做接口抽象，不同语言语法特性都不一样，每个语言有最好的实现方式，这时候靠的是白皮书，不是明面上的 interface。"
- "要设计一个跨平台的接口，本身就搞笑，实现了也是被人骂的份。"
- "要么接口足够底层，然后接口实现复杂；要么接口高层，性能一托。"

这是 Moli 的强硬观点，有反对声音——但他给出了清晰的论证：抽象在哪一层，决定了每平台实现的"天花板"；抽象定在业务契约，才能让每平台发挥 native 优势。
