# Choice & Scope — 选型、工具与决策

Moli 对"选什么"和"什么时候重来"有自己的一套判断标准。核心：**实证和生态优先**，不追"最新最潮"。

---

## 项目开始时先构建方便调试的环境，不要等 bug 出现再搭

**为什么**：上新系统时肉眼看数据能看出异常属于基本功；有好的调试工具调试效率提升不是一倍两倍，而是从"看不出问题"到"肉眼就能定位"。

**示例**：
```
新做一套配置系统：
  先写一个可视化 dumper，能打印每个中间状态
  调试时：一眼看出第 N 层数据不对，而不是在两个软件间反复切
```

Moli 原话："我优先会构建一个方便调试的环境。"

他还观察到，做寻路/配置这类系统时，**训练自己"肉眼看数据就能发现异常"**的能力，调试效率比 debugger 还高。这背后是因为他会在数据旁边随手做小工具/可视化 dumper。

---

## 选引擎看生态成熟度和用户基数，不是"最新最潮"

**为什么**：主流引擎（Unity / UE / Godot），你遇到的问题几乎都有人踩过，教程/社区/资源多，不容易被奇怪 bug 卡住；冷门引擎每个坑都要自己独立解决，投入的时间回不来。

**示例**：
```
bad: 听说 XX 引擎好高级，选 XX
good: Unity / UE / Godot 里选一个
     最熟/教程最多/你这个类型的游戏有多人做过的那个
```

Moli 原话：
- "面向找工作，Unity 有最多的机会。所以是 Unity。"
- "面向做独立游戏我觉得还是 Unity，或是你最熟的引擎。Unity 是因为资源多、教程多、用的人也多，你不容易被卡住；而且用的人太多了，稳定，不会有奇怪的问题。"

关于冷门引擎的嘲讽：
> "冷门引擎跃跃欲试？那必须是 Flare3D 引擎，去吧。" / "ogre 3D，厚重的历史积淀。"

（这些话是反讽——意思是别折腾这些已经死掉的东西。）

---

## AI 编程最擅长材质/shader 和工具代码，最不擅长业务代码

**为什么**：
- 材质/工具类代码**边界清晰**，能独立验证（shader 对不对眼睛看得出来）
- 业务代码依赖**上下文、历史决策、未写进注释的约束**——AI 难以把握，改几次就乱

**示例**：
```
用 AI 爽的:
  写 shader / toon shader / 后处理效果
  写 Editor tool / 自动化构建脚本
  写 unit test

别太指望 AI:
  写关卡逻辑
  修业务 bug（特别是老项目的）
  改 gameplay 的调整
```

Moli 原话：
- "写材质是真的好用。写工具也好用。写业务就不好用了。"

更 nuanced 的观察：
- Moli 主要用 Claude 写代码；其他工具（Gemini / 豆包 / 千问）按任务混用
- 用 AI 的"手脚眼睛"模式（agent 可以读/写文件、编译、查 doc）效率远高于"只给它看代码片段"
- Agent 写代码失败时不要反复喂 token 让它改——直接人肉介入更快

详见 [data-storage.md](data-storage.md)。核心：单机游戏数据量对数据库来说太小，字典+序列化更合适。

## Godot 项目要准备好被反编译

**Moli 的原始观察**（仅此而已）："Godot 有一个很大的问题，就是容易被反编译。"

**含义**：Godot 的 .gd 脚本打包后比商业引擎（Unity 的 IL2CPP / UE 的 C++）更容易逆向。

**影响**：
- 独游 / Demo / Jam 项目：基本无所谓
- 商业项目、怕被破解的 Gameplay 或付费 gate：要留意

**Moli 没说**具体应对策略——下面这些是常见做法，由 Claude 补充（非 Moli 直接观点）：
```
- 关键逻辑移到 C# 模块（Godot Mono 版编译成 DLL）
- 付费 / 成就校验走服务端
- 自己实现脚本加密或资源加密层（成本高）
```

---

## 需要多平台发布的项目首选 Unity

**为什么**：Unity 是目前**唯一**能在不显著增加工作量的前提下商业级输出到以下所有平台的引擎：
- Android / iOS
- H5 / 微信小游戏
- Windows / Steam / Mac / Linux
- Switch

UE 的 H5 基本废了，手游/PC 常要两套工程；Godot 稳定性还没到商用级别；Cocos 只有 H5 强。

**Moli 原话**："现在只有 Unity 可以做到一个项目，甚至是重型项目，可以在不增加太多额外工作量的情况下，商用级别的导出 Android、iOS、H5、微信小游戏、Windows、Steam、Mac、Linux、Switch。UE 的话 H5 基本没了，手机和 PC 基本两套，不知道有没有做到同一个工程的，即使可以，维护成本肯定比 Unity 大。"

**决策矩阵**：
```
纯 PC Steam:         UE / Unity 都行（看美术需求）
手游为主:            Unity 明显优势（生态+热更方案成熟）
H5 / 小游戏:         Unity / Cocos
跨全平台（含 H5）:   Unity 是目前唯一解
```

关于 Godot 为什么不在牌桌上（Moli 的判断）：
> "godot, 因为稳定性上还没到商用级别，所以不在牌桌上。"

对独游 Godot 仍然是好选择（生态足以、学习曲线平缓），但大规模商用 + 跨平台还没到。

## 游戏热更：走脚本热更 + 业务代码重启，不要追求 C++/C# 语言级热更

**为什么**：
- **C++ 虚拟机极难写**，Moli 原话："C++ 虚拟机太难写了，你不要一直追求 C++ 语言的热更。"
- **C# 语言级热更** 要做 Domain Reload，本质和重启等价："就算是 Unity 也是要重启最安全，不然就要用无数的方法去保证内存安全。"
- **真正实用** 的热更是 Lua/TS/第三方 C# 虚拟机（xlua、huatuo、puerts）承载业务逻辑，配合重启兜底

**示例**：
```
bad: 追求 C++ 代码热更，投入大量工程换极有限的收益
good: 业务逻辑走 Lua/TS 脚本（独立虚拟机）
      配置表走静态热更（下发新配置表）
      引擎层变更走版本更新，不做语言级热更
```

Moli 补充观点：
> "unity 也是第三方写了一个虚拟机。UE 一样的，可以接入 lua，可以接入 ts。"
> "UE 主攻 PC，不用这么麻烦的，直接替换 DLL 不就结了么。"（对 PC 游戏来说，整体替换 DLL 重启就是最简单的"热更"方案）

## 其他选型观察（Moli 的历史视角）

Moli 经历过：
- **Flash / AIR / stage3d** —— "flash 上限很低……stage3d API 难用的要死，shader 还是汇编级别的"
- **PC 网游 DX9/MFC 时代** —— 学引擎前都要学 Windows SDK
- **UE3 商用时代** —— 代码得买，现在已经开源
- **HTML5/WebGL 页游崛起** —— "现在的页游"
- **Unity 手游时代 (2015+)**
- **ECS/DOTS 探索**
- **AI 辅助编程时代**

他的总结：
> "现在的客户端基本都不会 DX 了。太底层了。"
> "独游引擎千奇百怪，多小众的都有，现在还有人用 Flash 做呢。"
> "我是互联网老古董，从 PC 网游时代一路做过来，这些技术栈我都接触过。"

这个视角给他的判断带来一种**去浮夸能力**——很多"新技术"他能看到它在历史里是第 N 次重演，所以不容易被营销词冲昏头。
