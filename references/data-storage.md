# Data Storage — 配置与存档

---

## 单机游戏不要用关系数据库/SQLite，静态数据字典+动态数据序列化文件

**为什么**：数据库的核心价值是**"超大量数据 + 复杂检索 + 部分载入"**；单机游戏动态数据撑死几 MB，全加载完整就够了，还带上 ORM/schema/迁移这些复杂度是负担。

**示例**：
```
bad: 单机塔防也搞个 SQLite 存玩家进度
     带上 schema 迁移、ORM、查询优化......

good:
- 静态配置表：启动时反序列化到 Dictionary<int, ItemData>
   程序运行中 O(1) 查表
- 动态数据（存档/玩家状态）：
   序列化成 JSON/MessagePack/binary 写到本地文件
   分个系统模块，每个系统一份存档
```

Moli 原话：
> "单机游戏对数据的需求很单，对于静态数据，多是 key-value 这种查询方式，所以自定表用来存，载入后建立字典足够了。动态数据这边，撑死了也就一两 MB 的数据量，分个系统模块，序列化一下保存在本地也够了。"
> "数据库是用来管理超大量数据，用来快速在超大量数据中使用复杂条件检索出有用信息的，特点之一就是管理的数据预期大小已经无法全放在内存里了……这东西不是不可以用在单机游戏上，就是有点浪费。"

---

## 什么时候确实需要数据库

（Moli 的反面例证，帮你判断）：

- **网络游戏 / MMO / SLG** —— 数据量大、多不同查询方式、多玩家并发读写：**需要**
- **长期累积玩家行为数据（BI / analytics）**：**需要**
- **单机游戏的"我有 100 万个物品 ID"**：不需要。100 万个 int-key 的字典才 ~10MB，全加载进去性能最好

---

## 大型配置表的极致优化（Moli 的做法）

单机/网游都适用。对 ≥ 10k 条的配置表，他的做法：

1. **1 万条以下**：哈希预处理，做到无碰撞的 O(1) 查找
2. **1 万条以上**：B+ 树分层载入，按需读索引页再读数据行
3. **字符串常量**：去重连成字符串常量块，按需加载
4. **索引与数据分离**：索引进内存，数据区按行 seek 读
5. **所有配置结构体化**：内存连续，cache 友好

这不是"做到极致"才值得学——是"真做大表时的通用架构"。如果你是小型单机，简单字典足够；只有数据规模顶到内存/启动性能边界时才往这些方向走。

Moli 原话（做配置优化的自白）：
> "为了优化配置这块，我感觉我快把配置写成一个数据库了。上了各种优化手段：比如 1 万条以下用哈希预处理做到无碰撞，1 万条以上走 B+ 树。再比如分出索引和数据区，只加载索引，数据查询时按需按行读。再比如索引，如果用 B+ 树的话，分层载入内存，不是一下子载入的。再比如对字符串常量去重，把它连成字符串常量块，按需加载。然后配置表都是结构体的，内存连续。"
