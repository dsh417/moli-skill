# Multiplayer — 联机 / 网络同步

Moli 在端游时代就做 MMO/SLG 服务器，对联机的复杂度有切身体会。他对小团队的建议非常直接：**评估联机成本的时候别天真。**

---

## 独游做联机优先 Steam P2P，不要自己架中心服务器

**为什么**：
- 玩家主机在玩家网络环境里，纯自建 P2P 会因内网不可达失败
- 自建中心 server 有持续运维+带宽成本
- Steam P2P 提供免费 NAT 穿透/中转

**示例**：
```
bad: 租云主机跑 dedicated server 撑玩家联机
good: 用 Steamworks SDK 的 ISteamNetworkingSockets
      依托 Steam 的中转/打洞基础设施
```

Moli 原话："主机是运行在玩家的网络环境中……可能是内网，其它玩家根本访问不了。所以 Steam 的 P2P 才有意义，他提供了免费的穿透服务，开发者可以不用再花钱维护个 server 了。"

---

## 估联机工作量"只多 20%"就是严重低估——实际 2-3 倍打底

**为什么**：帧同步或状态同步涉及房间、重连、延迟补偿、作弊检测、断线处理、存档同步、回滚……远不是"映射一下接口"能完事的。

**示例**：
```
心里估 1.2 倍 → 实际 2-3 倍打底
先砍掉联机需求、打磨单机，有余力再做
```

Moli 原话（回 loop 说"框架做好后只多 0.2 倍工作量"）："并不会，哪怕帧同步这种方案都不会，更不要说状态同步了。如果你的想法里只增加 0.2，那百分之百是你想的过于简单了。"

---

## 有物理的联机：帧同步+定点数 或 中心服务器，不要本地各算+定时回滚

**为什么**：浮点物理 + 初始位置/时间毫厘之差，结果相差十万八千里；本地各算+回滚会出现"上次回滚还没补间完，下次状态又差十万八千里"的死循环，球看上去到处乱跳。

**示例**：
```
bad: client 各自跑完整物理，每秒回滚对齐
     → 高速运动时补间一直追不上，球到处跳

good A (中心服务器 + 状态同步):
     client 只播放，server 跑物理并广播状态
     向量变时立刻同步，没变也 1-2s 同步一次做保活

good B (帧同步 + 定点数):
     所有 client 跑定点数物理（git 上有开源定点数物理库）
     投入同一帧序列的输入，各自独立计算结果必然一致
```

Moli 原话（分析为什么混合方案不行）：
> "物理这块运动的参数太多了，随便来一个参数不一致，就会导致结果相差很大，你不用这种方式的话，在不同的平台上球表现的差异可能会很大，你要不停地回滚。"
> "速度快的情况下，你上次的还没补间完，下一次又差十万八千里了，然后一直在补间。"

## 决策表

| 场景 | 推荐 |
|---|---|
| 独游 / 小团队 / 联机是次要功能 | Steam P2P + 状态同步 |
| 需要强确定性 / 回放 / 作弊防护 | 帧同步 + 定点数物理 |
| 大量玩家 / 持久世界 / 商业规模 | 中心服务器 + 状态同步 |
| 有物理模拟 / 高速运动 | **禁用** "本地各算+定时回滚"混合 |

---

## 常见坑（Moli 踩过的）

1. **"只是多写个房间管理"** —— 低估了重连、断线、房主迁移的复杂度
2. **"局域网做完加个 IP 就能外网"** —— 不考虑内网/NAT 不可达
3. **"定时同步整个世界"** —— 带宽炸掉，改成"向量变化时同步"
4. **"物理本地各算定时纠正"** —— 高速物体永远在补间震荡
