# Pathfinding & Movement Feel — 寻路与移动手感

Moli 8 年前做过类 C&C / 红警式 RTS，里面的寻路/编队/手感问题都亲自踩过。

---

## 编队寻路：每个单位独立算路径，只在最终汇聚点等齐

**为什么**：整队一起算到目标后再用 RVO 分散会出现前到的单位停下来等后到的，表现上像僵尸一卡一卡；独立寻路时，汇聚只发生在末端，过程自然。

**示例**：
```csharp
// bad
var path = PathfindFormation(unitGroup, target);
// 所有单位同步走这条 path → 看起来很刚体、很僵尸

// good
foreach (var unit in group) {
  unit.Path = PathfindAStar(unit.pos, unit.slotInTargetFormation);
}
// 每个单位独立走，天然会在目标处自动汇聚
```

Moli 原话："你寻路是对整个队伍作为一个单位的寻路吧？……你在走路时，不要一起算到目标位置，然后再由 RVO 走到下一个点。你分开来，一个个单位解决。这样就不存在前面到了要停着等的现象——等这件事，只会发生在最终目标处。"

---

## A* 网格寻路结果要做二次平滑（string-pulling）

**为什么**：原始 A* 输出是网格化路径，会保留大量直连通的中间点，单位走起来是锯齿状拐弯。

**算法**：
```
从起点 i 开始，尝试直连 path[i+1], path[i+2], ...
直到某个 path[k] 直连不通为止（被障碍阻挡）
把 path[i..k-1] 替换为单条直线，i = k-1，继续
```

Moli 原话："只保留完全无法优化掉的拐弯的点——这种点是优化不掉的，因为在拐点处有障碍。"

---

## 八方向 A* 路径已经够直，不需要平滑；JPS 才需要

**为什么**：八方向 A* 本身就能走斜线，结果很接近视觉最短；JPS 由于 jump-point 策略会跳过很多中间点，输出路径方向更呆板，string-pulling 收益大。

**示例**：
```
8-dir A*: 结果可直接使用
JPS: 建议加 string-pulling 后处理
```

---

## 编队移动要预测到达时间；中途落后按比例提速

**为什么**：避免编队移动时前快后慢导致整队停顿等待；中途动态调速能让队伍整体看起来平滑抵达。

**示例**：
```csharp
// 出发时
expectedT = distance / baseSpeed;

// 每帧
if (elapsed / expectedT > traveled / distance) {
  speed *= 1.05;  // 落后了，小幅提速
}
// 末端允许小范围停下等齐
```

Moli 原话："起始就可以预测计算出移动的时间，在路途中，发现时间不够用，就按比例加大移动速度。"

---

## 单位移动起步加速度大、刹车减速度小，表现对比强烈

**为什么**：对称的加减速会显得"肉"；不对称（快起动、缓停止）在 RTS/动作游戏里看起来更响应、不僵硬。

**示例**：
```
反例: accel = decel = 10
正例: startAccel = 50, stopDecel = 5
```

Moli 原话："你起始时把加速度变的足够大，停下来时足够小，就可以有很强烈的表现对比了。"

---

## 背景：Moli 的 RTS 移动设计原则

Moli 在 C&C 风格 RTS 里解决"像僵尸"问题的完整思路：
1. 单位独立寻路（而非编队共享路径）
2. A* 结果做 string-pulling 平滑
3. 移动预计时间，落后提速
4. 起步加速度大、刹车减速度小
5. "等齐"动作只发生在最终汇聚点

他八年前就靠这套解决了问题——看似简单但每一条都经过踩坑。
